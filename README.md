# Startup Failure Prediction MVP

Snapshot-based, time-windowed failure-risk model for the system described in `startup_failure_prediction_brief.md`.

## How the labels work

Each training row is a **company snapshot** — a company at one point in time. A snapshot only uses information known at or before `snapshot_date`.

For a horizon `N` years (default `N = 3`, configured in `src/startup_failure_prediction/config.py`):

- `label = 1` if the company **failed within N years** after `snapshot_date`
- `label = 0` if the company was **still observed alive at `snapshot_date + N years`**
- censored (excluded by default) if we cannot tell yet — e.g. a company founded recently whose horizon has not elapsed

This removes the apples-to-oranges comparison of "failed vs operating" that the previous version used. A company that survives long enough now generates several `label=0` snapshots at different ages, and a company that fails generates several `label=1` snapshots leading up to the failure.

## Data layout

Two CSVs feed the snapshot generator:

- `data/companies_raw.csv` — one row per company. Fields: founded_date, outcome (failed|operating), outcome_date, last_observed_date, industry / product_type / country, market_score, scalability_score, descriptions.
- `data/funding_events.csv` — one row per round. Fields: company_id, round_date, round_name, amount_usd.

Snapshots are generated by `src/startup_failure_prediction/snapshots.py` at yearly anniversaries and ~30 days after each funding round. Snapshot features (`age_years_at_snapshot`, `funding_total_usd_at_snapshot`, `funding_rounds_at_snapshot`, `days_since_last_round`) are computed from data available at that date — never with hindsight.

The included synthetic dataset (50 companies, ~370 usable snapshots) only validates the pipeline. Replace it with real data:
- `src/startup_failure_prediction/scrapers/loot_drop.py` — skeleton for failed companies (needs Playwright or reverse-engineered XHR; loot-drop.io is JS-rendered)
- `src/startup_failure_prediction/scrapers/survivors.py` — skeleton for surviving companies (Crunchbase API recommended)

## Pipeline commands

Rebuild the synthetic seed dataset (run when you change the seeds in the script):

```bash
python scripts/build_companies_raw.py
```

Train. Reads `data/companies_raw.csv` + `data/funding_events.csv`, generates snapshots, time-splits, fits a calibrated logistic regression with SentenceTransformer text embeddings, writes the model and report:

```bash
python -m startup_failure_prediction.train
```

Outputs:
- `models/startup_failure_model.joblib`
- `reports/evaluation_report.md` — ROC-AUC, PR-AUC, recall on failures, Brier score, reliability bins, top coefficients

Predict from a JSON payload that describes one snapshot:

```bash
python -m startup_failure_prediction.predict
python -m startup_failure_prediction.predict --input-file path/to/snapshot.json
```

A snapshot payload includes `snapshot_date`, the snapshot-time features, and descriptions. See `DEFAULT_EXAMPLE` in `src/startup_failure_prediction/predict.py`.

Run the API and browser UI:

```bash
python -m startup_failure_prediction.api --port 8000
```

## Why these metrics

The report focuses on ROC-AUC, PR-AUC, recall on failures, and a Brier-score / reliability-bin view because:

- ROC-AUC tells you how well the score orders companies — independent of the threshold and the base rate.
- PR-AUC matters when failures are the minority class; ROC-AUC can look optimistic when negatives dominate.
- Recall on failures matters because missing a failure is the costly error for most decision contexts.
- Brier score + reliability bins check that a 0.7 probability actually corresponds to ~70% failure rate. A calibrated probability is what makes the score usable as a decision input.

The split is time-based (snapshots before a cutoff date are train, on/after are test). Same company can appear in both train and test if its snapshots straddle the cutoff — that is intentional and matches deployment, where you score a company today using a model trained on yesterday's data.

## Important caveat

The included data is synthetic. Headline metrics (ROC-AUC ~1.0 on the test split) reflect the obvious patterns in the seed data, not real-world performance. Do not use the score for investment or operating decisions until `data/companies_raw.csv` and `data/funding_events.csv` are replaced with real records.
